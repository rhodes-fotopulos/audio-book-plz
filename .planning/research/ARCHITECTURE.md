# Architecture Patterns

**Domain:** Voice expression integration into EPUB-to-audiobook pipeline (v1.2)
**Researched:** 2026-03-06
**Overall confidence:** MEDIUM-HIGH (existing architecture well-understood; TTS conditioning approach requires empirical validation)

## Current Architecture (v1.1 Baseline)

Six sequential phases, each reading from and writing to disk:

```
Phase 1: Parse       EPUB -> segments.json
Phase 2: Attribute   segments.json -> characters.json + attributed.json + emotion.json
                     (includes scene_mood annotation + line override detection)
                     --- Ollama unload boundary ---
Phase 3: Match       characters.json + attributed.json -> voice_map.json
Phase 4: Synthesize  attributed.json + voice_map.json -> wavs/
                     (speech-act post-processing: volume/speed adjustments)
Phase 4.5: Verify    wavs/ + voice_map.json -> voice_consistency_report.json
Phase 5: Assemble    wavs/ -> chapters/*.mp3 + audiobook.mp3
```

### Existing Data That Is Generated But NOT Used by TTS

The v1.1 emotion system produces rich data that currently sits idle:

1. **`CharacterProfile.voice_baseline`** (VoiceBaseline model) -- pace, tone, energy, typical_emotion, description. Generated by LLM during character extraction. Stored in `characters.json`. **Not consumed by any downstream phase.**

2. **`CharacterProfile.voice_qualities`** (VoiceQualities model) -- pitch, pace, tone, accent. Used by trait_matcher and embedding_matcher for voice selection. **Not passed to TTS.**

3. **`emotion.json` scene moods** (SceneMood model) -- per-scene mood (8 categories), intensity (LOW/MEDIUM/HIGH), description. Generated by LLM via `scene_mood.py`. **Written to disk, never read back.**

4. **`emotion.json` line overrides** (LineOverride model) -- per-segment emotion overrides for extreme contrasts. Generated by LLM via `overrides.py`. **Written to disk, never read back.**

5. **`speech_act`** on AttributedSegment -- spoken/thought/shouted/whispered. **Used** by post_processor.py for volume/speed adjustments. This is the ONLY emotion data currently affecting audio output.

### The Duplicated Voice Fields Problem

`CharacterProfile` has TWO overlapping voice descriptions:

| Field | Type | Source | Used By |
|-------|------|--------|---------|
| `voice_qualities` | VoiceQualities(pitch, pace, tone, accent) | LLM extraction | trait_matcher, embedding_matcher |
| `voice_baseline` | VoiceBaseline(pace, tone, energy, typical_emotion, description) | LLM extraction | Nothing (dead code) |

Both have `pace` and `tone` fields with different vocabularies. `voice_qualities.pace` uses "fast"/"moderate"/"slow" while `voice_baseline.pace` uses "measured"/"rapid"/"languid"/"clipped". This duplication must be resolved before wiring data into TTS.

```

Internally calls:

```

**No emotion, style, or voice description parameters are passed to the TTS engine.**

## The Core Technical Constraint

**Qwen3-TTS Base model does NOT support an `instruct` parameter.** This is the fundamental constraint shaping the entire v1.2 architecture.

The Qwen3-TTS family has three model variants:

| Model | Voice Source | Emotion Control | API Method |
|-------|-------------|-----------------|------------|
| **Base** (currently used) | Voice cloning from ref_audio | None -- relies on text content for natural prosody | `model.generate(text, ref_audio, ref_text)` |
| **CustomVoice** | 9 preset voices only | `instruct` parameter (natural language) | `model.generate_custom_voice(text, speaker, language, instruct)` |
| **VoiceDesign** | Voice from text description | `instruct` parameter (natural language) | `model.generate_voice_design(text, language, instruct)` |

**You cannot combine voice cloning (ref_audio) with style instructions (instruct) in any single model call.** This was identified as the biggest risk in v1.1 research and remains the defining constraint.

### Viable Approaches for v1.2

**Approach A: Post-Processing Expressiveness (RECOMMENDED)**

Extend the existing post_processor.py approach to cover all three emotion layers, not just speech-acts. Use audio signal processing (volume, speed, pitch shift, reverb) driven by the emotion data.

- Voice identity: Qwen3-TTS Base with ref_audio (unchanged)
- Character voice style: Post-process with per-character speed/pitch offsets derived from voice_profile
- Scene mood: Post-process with scene-level parameter adjustments
- Line overrides: Post-process with override-specific adjustments (already partially done for speech-acts)

**Why this works:** The v1.1 speech-act adjustments (post_processor.py) already prove the pattern. Whispered (-4.5dB), shouted (+4.5dB, 1.08x speed), and thought (-3.0dB, 0.93x speed) produce audibly different results through pure signal processing. Extending this to scene mood and character style is the same pattern at different scopes.

**Approach B: Prompt Engineering in Text**

Modify the text itself before TTS to embed prosodic cues. For example, adding "[softly]" or "[angrily]" markers, or modifying punctuation (adding ellipses for hesitation, exclamation marks for emphasis). Qwen3-TTS Base respects these textual cues to some degree because it was trained on text with natural prosodic variation.

**Why risky:** The Base model was not trained with instruction tokens. Text modifications may produce artifacts or be ignored entirely. Needs empirical testing.

**Approach C: Reference Audio Selection Per Emotion**

Generate a library of emotion-styled reference clips per character using VoiceDesign or CustomVoice, then swap reference audio based on scene mood. The Base model's voice cloning will partially adopt the emotional quality of the reference.

**Why risky:** Requires generating and managing multiple reference clips per character. Voice consistency across emotion variants is unpredictable. Adds significant complexity.

### Recommended Architecture: Approach A with Approach B as Enhancement

Use post-processing as the primary expressiveness mechanism (reliable, deterministic) and experiment with text-based cues as a secondary enhancement (may improve or may degrade -- needs testing).

## Recommended Architecture (v1.2)

### New Component: `src/synthesis/expression.py` (NEW)

Central module that resolves the three emotion layers into concrete audio processing parameters.

```python
@dataclass
class ExpressionParams:
    """Resolved expression parameters for a single segment."""
    # From voice_profile (constant per character)
    base_speed_factor: float = 1.0    # derived from pace
    base_pitch_shift_st: float = 0.0  # derived from tone/energy (semitones)

    # From scene mood (varies per scene)
    mood_volume_db: float = 0.0
    mood_speed_factor: float = 1.0

    # From line override or speech-act (rare, per segment)
    override_volume_db: float = 0.0
    override_speed_factor: float = 1.0
    override_pitch_shift_st: float = 0.0

    # Combined (computed)
    @property
    def total_volume_db(self) -> float: ...
    @property
    def total_speed_factor(self) -> float: ...
    @property
    def total_pitch_shift_st(self) -> float: ...
```

### Modified Component: `src/synthesis/synthesizer.py` (MODIFY)

The synthesis loop must:
1. Load `emotion.json` at start
2. Load `characters.json` at start (for voice_profile)
3. Build scene mood lookup (segment_id -> SceneMood)
4. Build override lookup (segment_id -> LineOverride)
5. For each segment: resolve expression params, generate audio, apply expression

Key change in the inner loop:

## Integration Points (Detailed)

### Integration Point 1: emotion.json -> synthesizer.py

**Currently:** `run_synthesis()` receives `attributed_segments` (list[dict]) and `voice_map`. It does NOT load `emotion.json`.

**Change:** Add emotion loading at the top of `run_synthesis()`:

```python
# Load emotion data (optional -- graceful fallback if missing)
emotion_path = book_dir / "emotion.json"
emotion_data = None
if emotion_path.exists():
    with open(emotion_path) as f:
        emotion_data = json.load(f)

# Build lookups if emotion data available
scene_mood_lookup = {}  # segment_id -> SceneMood dict
override_lookup = {}    # segment_id -> LineOverride dict
if emotion_data:
    for ch_str, ch_data in emotion_data.get("chapters", {}).items():
        for scene in ch_data.get("scenes", []):
            for seg_id in range(scene["start_segment_id"], scene["end_segment_id"] + 1):
                scene_mood_lookup[seg_id] = scene
        for override in ch_data.get("overrides", []):
            override_lookup[override["segment_id"]] = override
```

### Integration Point 2: characters.json -> synthesizer.py

**Currently:** `run_synthesis()` does NOT load character profiles. It only uses `voice_map` for speaker-to-clip mappings.

**Change:** Load character profiles for voice_profile data:

```python
characters_path = book_dir / "characters.json"
voice_profiles = {}  # character_name -> VoiceProfile dict
if characters_path.exists():
    with open(characters_path) as f:
        characters_data = json.load(f)
    for char in characters_data:
        name = char.get("name", "")
        vp = char.get("voice_profile") or char.get("voice_qualities", {})
        voice_profiles[name] = vp
```

### Integration Point 3: voice_profile -> trait_matcher.py

**Currently:** `_build_character_description()` reads `character.voice_qualities` (pitch, pace, tone, accent).

**Change:** Read from `character.voice_profile` instead. Add energy, typical_emotion, and description to the text description. The voice_profile field contains all the old fields plus new ones.

### Integration Point 4: voice_profile -> embedding_matcher.py

**Currently:** `_build_character_text()` reads `character.voice_qualities` attributes.

**Change:** Read from `character.voice_profile`. Include description field for richer embedding.

## Patterns to Follow

### Pattern 1: Layered Expression Resolution

**What:** Resolve expression through three layers with clear precedence: line override > scene mood > character baseline > speech-act. Each layer is optional.

**When:** Every segment during synthesis.

**Why:** Separates data production (LLM phase) from data consumption (synthesis phase). Each layer can be developed and tested independently.

```python
def resolve_expression(segment, voice_profile, scene_mood, line_override, speech_act):
    params = ExpressionParams()

    # Layer 1: Character baseline (constant per character)
    if voice_profile:
        params.base_speed_factor = PACE_MAP.get(voice_profile.get("pace"), 1.0)
        params.base_pitch_shift_st = ENERGY_PITCH_MAP.get(voice_profile.get("energy"), 0.0)

    # Layer 2: Scene mood (varies per scene)
    if scene_mood:
        mood = scene_mood.get("mood", "neutral")
        intensity = scene_mood.get("intensity", "medium")
        mood_params = MOOD_PARAMS.get(mood, MOOD_PARAMS["neutral"])
        multiplier = INTENSITY_MULTIPLIER.get(intensity, 1.0)
        params.mood_volume_db = mood_params["volume_db"] * multiplier
        params.mood_speed_factor = mood_params["speed_factor"]

    # Layer 3: Line override takes precedence over scene mood
    if line_override:
        override_mood = line_override.get("emotion", "neutral")
        override_intensity = line_override.get("intensity", "high")
        override_params = MOOD_PARAMS.get(override_mood, MOOD_PARAMS["neutral"])
        multiplier = INTENSITY_MULTIPLIER.get(override_intensity, 1.0)
        params.override_volume_db = override_params["volume_db"] * multiplier
        params.override_speed_factor = override_params["speed_factor"]
        # Override replaces scene mood, not additive
        params.mood_volume_db = 0.0
        params.mood_speed_factor = 1.0

    # Speech-act adjustments (existing system -- orthogonal to emotion)
    if speech_act != "spoken":
        sa_params = SPEECH_ACT_PARAMS.get(speech_act, SPEECH_ACT_PARAMS["spoken"])
        params.override_volume_db += sa_params["volume_db"]
        params.override_speed_factor *= sa_params["speed_factor"]

    return params
```

### Pattern 2: Graceful Degradation

**What:** Every new data dependency is optional with sensible defaults. Missing emotion.json = no expression adjustments. Missing voice_profile = no character baseline.

**When:** Any integration point where v1.2 data feeds into an existing phase.

**Why:** Backward compatibility. Users with existing v1.1 output can re-run synthesis without re-running attribution. New runs get full expression; old runs keep working.

### Pattern 3: Voice Profile Migration

**What:** When loading `characters.json`, check for both old schema (voice_qualities + voice_baseline) and new schema (voice_profile). Auto-convert old to new at load time.

**When:** Loading characters.json in any downstream phase.

**Why:** Allows re-running synthesis against existing characters.json without re-running attribution.

```python
def load_voice_profile(char_data: dict) -> dict:
    """Load voice_profile, with fallback migration from old schema."""
    if "voice_profile" in char_data:
        return char_data["voice_profile"]
    # Migrate from old schema
    vq = char_data.get("voice_qualities", {})
    vb = char_data.get("voice_baseline", {})
    return {
        "pitch": vq.get("pitch", "unknown"),
        "pace": vb.get("pace", vq.get("pace", "unknown")),
        "tone": vb.get("tone", vq.get("tone", "unknown")),
        "accent": vq.get("accent", "unknown"),
        "energy": vb.get("energy", "unknown"),
        "typical_emotion": vb.get("typical_emotion", "neutral"),
        "description": vb.get("description", ""),
    }
```

## Anti-Patterns to Avoid

### Anti-Pattern 1: Adding instruct to QwenTTSEngine.generate()

**What:** Passing an emotion instruction string to the Base model's generate call.

**Why bad:** The Base model ignores it. Already documented in PROJECT.md key decisions: "Base model ignores instruct prompts with cloned voices; post-process volume/speed instead." Adding the parameter creates a false API that suggests functionality that does not exist.

**Instead:** Keep the engine interface unchanged. All expression is post-processing.

### Anti-Pattern 2: Cumulative Expression Stacking

**What:** Adding all three layers' adjustments together (character baseline + scene mood + line override = potentially huge combined adjustment).

**Why bad:** A character with "animated" energy (+2dB) in an "anger HIGH" scene (+4.5dB) with a "shouted" speech-act (+4.5dB) would get +11dB total -- severe clipping. Combined speed factors could produce unnaturally fast or slow speech.

**Instead:** Use layer precedence (override replaces mood, not adds to it). Clamp combined values to safe ranges. The speech-act system is the exception -- it is orthogonal to emotion and adds to the override/mood layer.

### Anti-Pattern 3: Modifying emotion.json Schema

**What:** Changing the emotion.json output format to accommodate synthesis needs.

**Why bad:** emotion.json is produced by the LLM attribution phase. The synthesis phase should adapt to the data as-is. Changing the schema would require re-running attribution for existing books.

**Instead:** The expression resolver translates emotion.json's 8-category EmotionCategory + MoodIntensity into audio processing parameters. The mapping lives entirely in synthesis code.

### Anti-Pattern 4: Per-Character TTS Model Loading

**What:** Loading different Qwen3-TTS variants (Base for some characters, CustomVoice for others) to get emotion control where possible.

**Why bad:** Model loading takes 5-10 seconds. Swapping models per segment or per character would add enormous latency. On 16GB memory, two models cannot coexist.

**Instead:** Use one model (Base) for all synthesis. Expression is post-processing.

## Suggested Build Order

Dependencies flow in this order:

```
1. Unify voice_profile (models.py)
   |
   +-> 2a. Update trait_matcher.py
   |   2b. Update embedding_matcher.py
   |   2c. Update extractor.py (LLM prompts)
   |
   3. Create expression.py (resolver)
   |   (depends on understanding voice_profile + emotion models)
   |
   4. Extend post_processor.py (mood + profile params)
   |   (depends on expression.py for ExpressionParams)
   |
   5. Wire synthesizer.py (load emotion.json + characters.json, call expression)
   |   (depends on expression.py + post_processor.py)
```

### Recommended Sequence

**Phase 1: Data Model Unification**
- Merge voice_qualities + voice_baseline into voice_profile in models.py
- Add migration helper for old schema
- Update extractor.py LLM prompts for unified schema
- Update trait_matcher.py and embedding_matcher.py

**Phase 2: Expression System**
- Create expression.py with ExpressionParams and resolve_expression()
- Define MOOD_PARAMS and INTENSITY_MULTIPLIER mappings
- Define PACE_MAP and ENERGY_PITCH_MAP for voice_profile -> audio params
- Unit test the resolver with all layer combinations

**Phase 3: Post-Processing Extension**
- Extend post_processor.py with apply_expression()
- Add pitch shifting capability (using numpy interpolation, already done for speed)
- Keep existing apply_speech_act_adjustments() as backward-compatible entry point
- Clamp all combined parameters to safe ranges

**Phase 4: Synthesis Wiring**
- Wire emotion.json loading into synthesizer.py
- Wire characters.json loading into synthesizer.py
- Build segment-to-scene and segment-to-override lookups
- Replace speech-act-only adjustment with full expression resolution
- Maintain backward compatibility (no emotion.json = no adjustments)

### Phase Ordering Rationale

- **Models first** because everything downstream depends on the unified voice_profile schema.
- **Expression resolver before post-processor** because the resolver defines ExpressionParams which the post-processor consumes.
- **Post-processor before synthesizer wiring** because the synthesizer calls the post-processor -- both must be ready before integration testing.
- **Synthesizer wiring last** because it is the integration point that brings everything together.

### What Can Be Parallelized

- Phase 1 (data model) and Phase 2 (expression resolver) are partially independent -- the resolver uses the model types but can be developed with mock data.
- Phase 3 (post-processor extension) can be developed with mock ExpressionParams before the resolver is complete.
